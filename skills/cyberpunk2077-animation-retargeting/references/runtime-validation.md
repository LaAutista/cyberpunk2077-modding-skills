# Diagnostic slice, accepted beta and runtime

As soon as one source clip, mapping and writable compatible container exist, take
that clip through native readback and complete Blender playback review. Resolve
visible motion/contact defects offline. Do not port a complete set or reconstruct
the engine before demonstrating one acceptable connected sequence.

An **isolated diagnostic package** may be prepared offline with disclosed defects
and a FAILED/OPEN visual gate. This does not authorize installation. The
[mandatory Blender and user-preview gate](../SKILL.md#mandatory-blender-review-before-installation)
applies to diagnostic packages too: show smooth complete motion, retain failures,
and wait for explicit acceptance of the identified candidate. A user may expressly
accept a displayed, named defect for a specific diagnostic; generic permission to
test or deploy is not that waiver. Never overwrite or promote the working baseline.
A native mismatch, changed unrelated resources or unidentified shipped bytes
blocks even the diagnostic package.

An **accepted beta** requires the existing
[full-motion Blender visual receipt](../../cyberpunk2077-modding/references/animation-retargeting/qa-debugging.md#mandatory-blender-visual-acceptance)
for the current candidate: matched source/target throughout the timeline and
transitions, full 360-degree coverage including above/below/hidden areas and all
relevant digit/contact/mechanism close-ups. Visible defects fail a claim of clean visual acceptance.
Generating renders is not inspecting them. A diagnostic runtime pass does not
waive visual failure or authorize full-set expansion.

Record package hash, source/target/container hashes, game/tool versions, selected
clip and body variant, prerequisites, mutually exclusive packages and effective
profile/override. Extract the isolated archive and compare every resource to the
intended checked output. Leave deployment to the authorized manager/profile path.

Before an authorized user runtime test, identify the remaining question that
Blender review did not resolve and verify the user's preview acceptance. Do not
ask the user to rediscover a known visible failure in game.

For that runtime test:

1. Preserve the profile and working package; enable only the intended test variant
   with its recorded dependencies and confirm which resource override wins.
2. Trigger the named clip and observe beginning, middle and ending. Confirm the
   expected motion actually replaces the intended state.
3. Enter/leave the state, loop if applicable, test relevant interruptions and
   repeat in each affected first-person/body/weapon variant.
4. Inspect hand/weapon contact, controls/IK, mechanisms and visibility; check
   audio/events only if part of this clip's acceptance scope. Record deviations.
5. Record the user's confirmation or failure with exact archive hash, environment,
   conditions and observations. Restore the baseline through the preserved profile
   if the diagnostic fails or the user requests rollback. Keep an accepted build
   installed when that is the authorized outcome; rollback is containment, not a
   substitute for repairing the requested approved motion.

Expected success is correct named motion with stable transitions and required
contact/IK in that tested scope. Missing game access leaves runtime OPEN with
these manual steps. Only identified user confirmation earns USER_RUNTIME_VERIFIED;
another build's report or static graph inspection cannot. Expand to other clips
after applicable gates for a new route pass. An established route can batch
compatible actions, reviewing their full changed motion and transitions together;
it does not need an isolated runtime approval cycle for every clip. A later package needs its own
runtime evidence; a changed hash invalidates reuse of the old confirmation.


Explicit user release acceptance can retain named known defects or native
fallbacks. Record the exact artifact, user's acceptance, exceptions and untested
combinations. Do not turn that into a flawless visual/source-parity pass, and do
not override the user's acceptance criteria with a broader assistant checklist.
The [MP5 1.0 case](mp5-workflow.md) demonstrates this distinction.
