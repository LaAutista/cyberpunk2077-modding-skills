# Cyberpunk mod development playbook

This is working knowledge for the coding agent. Read the relevant source documentation before implementing the specific feature; use this guide to choose the approach and avoid repeating known mistakes. Source snapshots were collected on 2026-10-06/07. They do not establish that a later game or framework build is compatible.

## Choose the implementation layer

| Requested change | Starting point | What to establish before coding |
| --- | --- | --- |
| Item stats, loot, vendors, vehicle parameters, record variants | TweakXL YAML | Existing record, property types, inherited arrays, record relationships |
| Combat rules, scripted interactions, equipment behavior | redscript | Existing method signature, call order, state ownership, other wrappers |
| Lua utility, prototype, hotkey, ImGui overlay | CET | Initialization event, input registration, draw/update behavior, session availability |
| New model, texture, appearance, clothing or weapon asset | WolvenKit + ArchiveXL; often TweakXL | Depot paths, resource dependencies, factory mapping, appearances and records |
| Native in-game menus and widgets | redscript + Codeware; WolvenKit for widget resources | UI layer, controller lifetime, widget ownership and cleanup |
| Engine functionality absent from exposed scripts | RED4ext SDK, optionally RedLib | Exact binary version, ABI, allocator/handle ownership, registration lifecycle |

Several layers may be needed for one feature. A standalone item commonly needs a TweakDB record, an ArchiveXL factory entry, an entity/appearance chain, meshes/materials, localization and an icon. Changing only the record does not create the resources it references. Use [the source map](topic-map.md) to select the appropriate guide.

## redscript: behavior, hooks, names and types

Scripts use `.reds` and ship under `r6/scripts/<ModName>/`. Prefer a module namespace for your own types. Runtime lookups of a custom class require its fully qualified name; `NameOf<MyType>()` avoids duplicating that name where supported by the installed compiler. A module is a redscript namespace, not necessarily a mod folder. Conditional compilation with `ModuleExists` checks modules. [Modules](https://wiki.redmodding.org/scripting-cyberpunk/redscript/language-reference/modules), [conditional compilation](https://wiki.redmodding.org/scripting-cyberpunk/redscript/language-reference/modules/conditional-compilation), [structure names](https://wiki.redmodding.org/scripting-cyberpunk/redscript/language-reference/structure-names).

Use `@wrapMethod` to compose behavior and call `wrappedMethod` with the correct arguments and return handling. Decide whether custom work belongs before or after the underlying method by reading that method's implementation. `@replaceMethod` replaces behavior and can conflict with other replacements; use it when replacement is actually required. A new helper is an `@addMethod` or an ordinary method on your own class, not a wrapper around a nonexistent game method. Wrappers still require compatibility testing when several mods touch the same state. [Hook annotations](https://wiki.redmodding.org/scripting-cyberpunk/redscript/language-reference/hook-annotations).

An `as` downcast may produce an undefined reference. Check it with `IsDefined` before calling a method or accessing a field. `FromVariant<T>` needs the matching contained type. Do not invent native declarations based on a name; check game scripts, NativeDB, framework source or the SDK for the real signature. The current language guide documents no `continue`; use a guard or a helper function when skipping work. [Safe downcasting](https://wiki.redmodding.org/scripting-cyberpunk/redscript/common-patterns/safe-downcasting), [intrinsics](https://wiki.redmodding.org/scripting-cyberpunk/redscript/language-reference/intrinsics), [loops](https://wiki.redmodding.org/scripting-cyberpunk/redscript/language-reference/loops).

## Lifecycle and persistence

`ScriptableSystem` belongs to a game session and can persist marked fields in that save. Codeware's `ScriptableService` survives session changes; its persistent fields live in global storage shared across saves. `PersistentState` provides entity-scoped storage. Choose deliberately: a per-save quest flag does not belong in global service storage. Persistent nested objects need their own fields marked persistent. The documented unsupported types include `String`, `ResRef` and `Variant`; check the installed implementation before designing a format around them. [Persistence](https://wiki.redmodding.org/scripting-cyberpunk/redscript/language-reference/persistence), [Codeware lifecycle](https://github.com/psiberx/cp2077-codeware/wiki#lifecycle).

Codeware warns that keeping game-object references in services can prevent their normal disposal. Retain strong references only where ownership is required, prefer weak references for observing session objects, recheck validity when delayed work runs, and clear session state at the appropriate lifecycle event. Saving a transient entity ID does not turn it into a persistent identity. Codeware's dynamic entities have distinct `persistState` and `persistSpawn` options. [Codeware world and lifecycle reference](https://github.com/psiberx/cp2077-codeware/wiki).

`OnAttach` does not imply the player is ready. Use the documented player lifecycle or Codeware session/entity callbacks for the point you need. A service's `OnLoad` precedes game-system availability; `OnInitialize` is the documented point for accessing game systems. `Resource/Load` precedes post-processing, while `Resource/PostLoad` sees the processed resource. Use target filters when registering callbacks. Service callbacks normally persist until removed; other contexts default to session lifetime. Verify registration and teardown together so a reload does not duplicate listeners or leave callbacks targeting discarded state. [Player lifecycle](https://wiki.redmodding.org/scripting-cyberpunk/redscript/common-patterns/handling-player-life-cycle-events), [Codeware callback reference](https://github.com/psiberx/cp2077-codeware/wiki#game-events).

Use DelaySystem/DelayCallback for engine-scheduled delayed work. Keep a cancellation or invalidation strategy when its owner can disappear; verify the actual cancel API in the target game's declaration. A weak target must be checked again inside the callback. For reflective calls, check that the method exists and accepts the intended arguments. `cb` enables the short callback names used by the examples. [Delays](https://wiki.redmodding.org/scripting-cyberpunk/redscript/common-patterns/delaysystem-and-delaycallback), [generic callbacks](https://wiki.redmodding.org/scripting-cyberpunk/redscript/common-patterns/generic-callbacks), [Codeware reflection](https://github.com/psiberx/cp2077-codeware/wiki#reflection).

## CET: Lua and runtime tools

A CET mod has `bin/x64/plugins/cyber_engine_tweaks/mods/<ModName>/init.lua`. Register observers/overrides during `onInit`; that event does not mean a playable save is loaded. Check session/player availability for game-dependent work. Put ImGui drawing in `onDraw`; scope repeated work in `onUpdate` to the feature that needs it. The CET overlay events describe the CET overlay, not every in-game menu. [CET events](https://wiki.redmodding.org/scripting-cyberpunk/cyber-engine-tweaks/cet-functions/events).

`Observe` aliases `ObserveBefore`; `ObserveAfter` runs after the observed method. Instance callbacks receive the object first; static methods do not. Overloads/static hooks may need the full method name from NativeDB. `Override` changes the call chain, so preserve wrapped calls and returns when extending behavior. [Observe](https://wiki.redmodding.org/scripting-cyberpunk/cyber-engine-tweaks/cet-functions/observers/observe), [Override](https://wiki.redmodding.org/scripting-cyberpunk/cyber-engine-tweaks/cet-functions/observers/override).

Validate against CET's Lua environment, not a random newer Lua version. A syntax check cannot establish that CET bindings exist or that a retained engine object remains valid. Read [documentation corrections](documentation-corrections.md) before reusing the wiki's Lua performance examples.

## TweakXL: records and typed data

TweakXL reads `.yaml`, `.yml`, or `.tweak` files under `r6/tweaks`, including subdirectories. A flat is a typed value; a record groups properties and refers to other records by TweakDBID. For a complex new item or vehicle, clone a suitable base with `$base` and change only the intended properties. `$type` creates a record with defaults, which may omit required relationships. New free flats require an unambiguous type; existing properties can use implicit values because their types are known. [TweakDB](https://github.com/psiberx/cp2077-tweak-xl/wiki/TweakDB), [YAML syntax](https://github.com/psiberx/cp2077-tweak-xl/wiki/YAML-Tweaks).

An ordinary array assignment replaces that property. Use `!append-once`, `!remove` or another documented array operation when extending shared lists; inherited arrays also participate in these operations. Plain `!append` allows duplication, so choose intentionally. Inline records need `$type` where the relationship is polymorphic. TweakXL templates use `$instances` at the top level. The `icon` convenience property generates a UIIcon record and its corresponding `iconPath`. [YAML arrays, templates and icons](https://github.com/psiberx/cp2077-tweak-xl/wiki/YAML-Tweaks).

After runtime `TweakDBManager.SetFlat` changes a record property, call `UpdateRecord` to propagate it to existing record instances. `ScriptableTweak.OnApply` runs before GameInstance and game systems are ready. Keep that callback focused on database changes. A successful reload is not proof that a spawned object rebuilt all cached state. [Script extensions](https://github.com/psiberx/cp2077-tweak-xl/wiki/Script-Extensions), [tools and log path](https://github.com/psiberx/cp2077-tweak-xl/wiki/Modder-Tools).

## WolvenKit and ArchiveXL: resource pipeline

Create a real WolvenKit project for resource work. `source/archive` holds game resources, `source/raw` holds editable exports, and `source/resources` holds other files laid out relative to the game root. `packed` is generated output and may be recreated on packing. Keep original/editable inputs in source. [Projects](https://wiki.redmodding.org/wolvenkit/wolvenkit-app/usage/wolvenkit-projects).

Preserve mirrored paths between an exported file under `raw` and its target under `archive`. Mesh import needs an existing compatible container; a renamed GLB may no longer map to it. JSON import expects the WolvenKit serialization format, not arbitrary JSON. Texture imports have their own settings and can create standalone XBM files. Match texture group, gamma, alpha, orientation and compression to the intended use. For meshes, inspect rigs, submeshes, materials, LODs and import settings; a material JSON reimport can overwrite edits. [Import/export](https://wiki.redmodding.org/wolvenkit/wolvenkit-app/usage/import-export), [JSON](https://wiki.redmodding.org/wolvenkit/wolvenkit-app/usage/import-export/import-export-as-json), [models](https://wiki.redmodding.org/wolvenkit/wolvenkit-app/usage/import-export/models), [textures](https://wiki.redmodding.org/wolvenkit/wolvenkit-app/usage/import-export/textures).

Use a unique depot namespace for new resources. ArchiveXL extends factory and localization resources from a `.xl` configuration adjacent to the archive. These resources are game-format CR2W files even where an extension such as `.csv` or `.json` looks like ordinary text. Its dynamic appearances require the `DynamicAppearance` visual tag. Interpolated paths start with `*`; variants use the `appearance!variant` syntax, with conditional appearance/component selection defined by ArchiveXL. Localization should use unique secondary keys for new text. [ArchiveXL reference](https://github.com/psiberx/cp2077-archive-xl/wiki).

Validate the entire dependency chain, then pack and inspect what actually ships. WolvenKit file validation checks names, paths, material/appearance links and several format-specific invariants, but reports can be affected by which mod resources are visible. Passing validation is not equivalent to an in-game test. [File validation](https://wiki.redmodding.org/wolvenkit/wolvenkit-app/file-validation).

## Native plugins

Use RED4ext's documented exports and lifecycle for loading and type registration. SDK layouts and binary addresses are version-specific. Register native types/functions through the appropriate callbacks; a plugin load event does not imply game objects can already be created. Raw script handlers must consume parameters in order and advance past parameter termination as the SDK example requires. [RED4ext manual](https://docs.red4ext.com/), [RedLib](https://github.com/psiberx/cp2077-red-lib/blob/6822105d15d1b8bd1e6aae5e57827835e585cfe8/README.md).

Treat `Handle`, `WeakHandle` and their reference-count block as ownership-bearing types. Use constructors, assignments and SDK helpers rather than copying their bytes or inventing a refcount block. Do not mix allocation/deallocation conventions across the game and C++ runtime. Verify the target SDK's definitions and allocator interface when touching native objects. The linked SDK revision is a source reference; it is not automatic proof that every decoded field matches the installed executable. [Handle implementation](https://github.com/wopss/RED4ext.SDK/blob/ad7277714ad30d6885d7050c5ba24fa0102f6920/include/RED4ext/Handle.hpp).

## Packaging and verification

Ship the folders appropriate to the chosen framework. Legacy archives go under `archive/pc/mod`; REDmod has a distinct `mods/<name>` package and deployment flow. An archive's filename priority is not a universal load-order rule for script hooks or tweaks. Check the layer-specific documentation and actual mod manager resolution. [Archive load order](https://wiki.redmodding.org/cyberpunk-2077-modding/for-mod-users/users-modding-cyberpunk-2077/load-order), [official REDmod manual](https://www.cyberpunk.net/en/modding-support).

Use the configurable paths in [environment setup](environment.md). Source work belongs outside the game tree. Respect the user's existing manager/profile and deployment policy; do not infer authorization from these instructions. Record actual game/framework versions and which checks ran. For lifecycle-sensitive features, exercise load, save, reload, detach/re-equip and session transitions relevant to the change. Inspect the installed compiler/framework logs after the user-controlled test.

Keep source, packaged artifact, hashes and short implementation notes together. Update the local knowledge base with verified discoveries, linking the declaration or evidence that supports them. Report an unavailable in-game check plainly instead of calling a syntactically valid starter a working mod.
